# Phase 6: テスト拡充（回帰 grep）

## 6.1 目的

Phase 4 の VC（正の検証）に加え、**過剰削除を検知する fail path / 回帰 guard** を設計する。
最小差分原則（Phase 3 §3.5）に反し、誤って **残り 2 件（#351 / #484）の行**や「通知先」セクションまで削除していないことを保証する。

## 6.2 回帰検証ケース（RC-01〜RC-03）

| ID | コマンド | 期待値 | 守る対象 |
|----|----------|--------|----------|
| RC-01 | `gh issue view 524 --json body -q .body \| grep -c "Issue #351"` | `1` | post-release dashboard automation の行が残存していること（誤削除防止） |
| RC-02 | `gh issue view 524 --json body -q .body \| grep -c "Issue #484"` | `1` | Cloudflare Analytics monthly export の行が残存していること（誤削除防止） |
| RC-03 | `gh issue view 524 --json body -q .body \| grep -c "ubm-hyogo-ops"` | `1` 以上 | 「通知先」セクション（Slack channel `#ubm-hyogo-ops`）が残存していること |

> RC-01 / RC-02 は「#407 行のみを削除し、同テーブルの残り 2 行を温存できているか」を検証する。
> RC-03 は通知統合の本体（投稿先 channel）が消えていないことを保証する。残り 2 件の Slack 実装に必須のため。

## 6.3 fail path の意味づけ

| 異常シナリオ | 検知する RC | 期待される検知挙動 |
|--------------|-------------|--------------------|
| テーブルを丸ごと削除した | RC-01 / RC-02 | `0` を返し fail（誤削除を検出） |
| #407 行の代わりに #351 行を消した | RC-01 | `0` を返し fail |
| 「参照」節除去のついでに「通知先」節を消した | RC-03 | `0` を返し fail |

## 6.4 実行タイミング

- RC-01〜RC-03 は VC-01〜VC-06 と同じく **#524 本文編集（user-gated 反映）後**に実行する。
- VC（正の整合）と RC（負の回帰 guard）を一括で実行し、両者すべて期待値一致で検証完了とする。

## 6.5 判定基準

- VC-01〜VC-06 が全て期待値一致 **かつ** RC-01〜RC-03 が全て期待値一致のとき、Phase 6 PASS。
- RC のいずれかが fail した場合、過剰削除が発生しているため Phase 5 差分を見直し、残り 2 件の行・「通知先」節を復元する。
