## 3.2 真の論点

- **主問題（1 文）**: 親タスクが workflow を削除した確定帰結により、open issue #524 の通知統合スコープ 1 行目が実装不能化・参照 dangling 化しているが、#524 本文・ローカルミラーともに未整合のまま残っている。
- **1 提案に複数案件が混ざっていないか**: 混在なし。本タスクは「#524 の陳腐化整合」単一責務。残り 2 件の Slack 実装は明確に分離（#524 本体）。
- **why now**: 親タスク landed 済みで「issue 確定は親 PR merge 後」の不変条件が満たされた今が適時。
- **why this way（案A）**: event-based 通知（案B）は新規設計を伴い YAGNI。最小整合で current facts を回復するのが正。

## 3.3 因果と境界

- **バランスループ**: 「削除した workflow を参照する open issue が残る → 実装者が混乱 → 整合タスク起票 → #524 整合 → 混乱解消」。本タスクがループを閉じる。
- **意思決定権**: #524 残り 2 件のスコープ判断権は #524 本体実装者にある。本タスクは越境しない。
- **状態所有権**: GitHub issue 本文（リモート正本）とローカルミラー md（リポジトリ整合）の二者を同期。所有権の混在なし。

## 3.4 docs-only 妥当性の再確認（CONST_004）

- 「目的達成にコード変更が必要」な兆候（動作・改善・修正の含意）は存在しない → docs-only 判定は妥当。実装区分を覆さない。
