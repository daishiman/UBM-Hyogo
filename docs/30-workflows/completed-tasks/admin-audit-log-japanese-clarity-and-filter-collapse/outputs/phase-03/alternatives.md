# Phase 3 — alternatives（代替案とトレードオフ）

> 上流: `../phase-02/*`。検討した代替案・却下理由・採用根拠・ユーザー選択経緯を記録する。

## 軸 1: 操作コード・対象種別の表示方式

### 案 A（採用）: 日本語ラベルのみ表示（未登録のみ raw fallback）

- **構造**: `describeAuditAction` / `describeAuditTargetType` で生コードを日本語へ変換。未登録コードのみ生コードを fallback 表示。
- **メリット**:
  - 非エンジニア管理者にとってノイズ（生コード）が消え直感的（AC-3）
  - 用語集 SSOT 一元管理で表記揺れが起きない（AC-6）
  - 未登録でも情報欠落しない（raw fallback の安全弁）
- **デメリット**: 未登録コードは生コードのまま出る（SSOT 追記が必要・OOS で対処）

### 案 B: 操作コード併記（日本語 + 生コードを括弧で両表示）

- **構造**: `出席を追加（attendance.add）` のように日本語と生コードを併記。
- **メリット**: 技術者がコードを直接確認できる。
- **デメリット**:
  - 非エンジニア管理者には生コードがノイズ（主問題が半解決）
  - カード meta / チップが横長になり整列（C3）を阻害
  - ユーザー確定方針「生コード非表示」と不一致
- **却下理由**: ユーザー方針違反。非エンジニア向け直感性という価値に反する。

> **ユーザー選択経緯（AskUserQuestion 2026-06-11）**: 「操作コード・対象種別の表示」論点で**「日本語ラベルのみ表示（生コード非表示）。用語集 SSOT で変換し、未登録コードのみ情報欠落防止として生コードを fallback 表示」**を確定。案 B（併記）は明示的に不採用。

| 軸 1 比較 | 案 A 日本語のみ（採用） | 案 B 併記 |
| --- | --- | --- |
| 非エンジニア直感性（AC-3） | ◎ | △ |
| 整列（C3）への影響 | ◎ | △（横長化） |
| 情報欠落防止 | ◎（raw fallback） | ◎ |
| ユーザー方針整合 | ◎ | ✗ |
| 採否 | **採用** | 却下 |

## 軸 2: フィルタフォーム構成

### 案 A（採用）: 2 層段階開示（常時 5 + details 3）

- **構造**: よく使う 5 項目（操作の種類 / 実行者 / 期間×2 / 表示件数）を常時表示、上級者向け 3 項目（対象の種類 / 対象ID / 一括処理ID）を `<details>` に格納。
- **メリット**:
  - 初見の管理者は 5 項目だけ見えて負荷が低い（AC-2）
  - 既存 `FormField` + native `<details>` で実現（新規 primitive ゼロ・AC-10）
  - 詳細フィルタに値があれば open で適用中条件を隠さない
- **デメリット**: 詳細 3 項目を使うとき 1 クリック開く必要がある

### 案 C: 全項目フラット維持（現状のまま 8 項目並列・ラベルだけ日本語化）

- **構造**: 8 項目をフラットに並べたまま、ラベルのみ日本語化。
- **メリット**: 実装が最小（段階開示の構造変更不要）。
- **デメリット**:
  - 「8 項目フラットで初見負荷が高い」という主問題（R-5）が未解決
  - よく使う項目と高度な項目の優先順位が表現されない
- **却下理由**: 主問題（初見負荷）を解消できない。価値性が不足。

> **ユーザー選択経緯（AskUserQuestion 2026-06-11）**: 「フィルタフォーム構成」論点で**「よく使う項目を常時表示、上級者向けは『詳細な絞り込み』折りたたみへ格納。常時=操作の種類/実行者/期間(開始)/期間(終了)/表示件数、details=対象の種類/対象ID/一括処理ID」**を確定。案 C（フラット維持）は不採用。

| 軸 2 比較 | 案 A 段階開示（採用） | 案 C フラット維持 |
| --- | --- | --- |
| 初見負荷削減（AC-2） | ◎ | ✗ |
| 新規 primitive ゼロ（AC-10） | ◎（native details） | ◎ |
| 優先順位の表現 | ◎ | ✗ |
| ユーザー方針整合 | ◎ | ✗ |
| 採否 | **採用** | 却下 |

## 軸 3: details open 状態の管理方式

### 案 A（採用）: DOM 属性 `<details open={defaultOpen}>`（uncontrolled）

- **構造**: `defaultOpen = Boolean(targetType || targetId || batchId)` を初期描画時に算出し DOM 属性へ。以後のトグルはブラウザに委ねる。
- **メリット**:
  - 内部 `useState` を増やさず状態が単純（[VSCPKR-03]）
  - ネイティブ `<details>` の a11y / キーボード操作をそのまま得る（AC-11）
  - 適用中の高度条件があれば open で隠さない（AC-2）
- **デメリット**: open 状態を JS で完全制御できない（本タスクでは不要）

### 案 D: 内部 state 管理（`const [open, setOpen] = useState(...)` + controlled）

- **構造**: open を React state で保持し `onToggle` で制御。
- **メリット**: open を JS から任意に変更できる。
- **デメリット**:
  - 不要な状態追加で複雑化（uncontrolled で足りる）
  - ネイティブ details の挙動を二重管理するリスク
- **却下理由**: 要件（初期 open 既定の算出）に対し過剰。状態を増やさない方が単純で堅牢。

| 軸 3 比較 | 案 A DOM 属性（採用） | 案 D 内部 state |
| --- | --- | --- |
| 状態の単純さ（[VSCPKR-03]） | ◎（state 増やさない） | △ |
| a11y / キーボード（AC-11） | ◎（native） | ◎ |
| 初期 open 既定の算出 | ◎ | ◎ |
| 実装コスト | ◎ | △ |
| 採否 | **採用** | 却下 |

## 総括

3 軸の採用案（日本語のみ表示 + 2 層段階開示 + DOM 属性 defaultOpen）は、いずれも:
- ユーザー確定方針に整合（軸 1・軸 2）
- データ層・型に触れず表現層に閉じる（AC-9）
- 新規 primitive を生やさない（AC-10・native `<details>` 利用）
- 状態を最小に保つ（軸 3・[VSCPKR-03]）

MAJOR blocker なし。MINOR 3 件（placeholder grep / Guide 範囲 / 未登録 SSOT）は許容し Phase 4 へ進む。
