## 4条件評価

- **価値性**: 開発者全員のテスト実行基盤を vitest 3 系へ更新し、2.x の保守終了リスクと既知バグを回避。誰の何のコストを下げるか明確。
- **実現性**: 1サイクルで bump + lockfile + config + test 修正が収まる想定。651 spec のうち実 fail は C1〜C3 起因の局所と見込む（全書き換えではない）。
- **整合性**: vitest/coverage-v8 のバージョン一致、D1 pool 設計維持、react alias 維持で矛盾なく閉じる。
- **運用性**: CI 5 shard の green 回復を完了条件に置き、coverage-guard で回帰を担保。後続 resume も `pnpm install` 起点で再現可能。

## 因果ループ（簡易）

- 強化ループ: bump → RED fail 観測 → 分類精度向上 → 修正の的確化 → GREEN 到達速度向上。
- バランスループ: 修正範囲拡大 → プロダクトコード巻き込みリスク増 → 「責務境界（Phase 2）」で抑制 → 範囲をテスト/config に収束。

## エスカレーション条件（CONST_007 例外の発火点）

以下のいずれかを RED 観測時に検知したら、実装を止めてユーザーへ確認する:

1. 単一の破壊的変更で **数百件規模** のテスト書き換えが必要（局所修正で収まらない）。
2. プロダクトコードの挙動変更なしには green にできない fail がある（例: vitest が前提とする実装契約の変化）。
3. coverage 閾値を実測ずれの範囲を超えて下げないと通らない（品質低下を伴う）。

> いずれも現時点の調査では発生可能性は低い（C1〜C3 は期待値修正で解決する性質）。

## 残課題（Phase 4 への申し送り）

- RED 採取は shard 単位で行い、fail を C1〜C8 のどのカテゴリかタグ付けして記録する（Phase 4 のテスト設計表に反映）。
- `test('name', fn, {opts})` 形式（C8）の有無は `grep -rn` で事前検出しておく。

## 判定

**PASS** — 設計は実装可能な粒度に達している。Phase 4（テスト作成 / RED 設計）へ進む。
